# Local execution для Direct provider

Local запускает инструменты непосредственно в среде backend Automaker. Если backend
работает в Docker, это контейнер Automaker, а не новый проектный контейнер. Если backend
работает на хосте, инструменты работают на хосте с правами того же пользователя.
Автоматического повышения прав нет: если сам backend запущен от root/Administrator,
агент наследует эти права. Это **не sandbox**.

## Как включить

1. Откройте Global Settings → Execution Environment либо Project Settings →
   Execution Environment для индивидуального выбора.
2. Выберите Local и сохраните конфигурацию. В проекте можно оставить наследование.
3. Прочитайте предупреждение, установите checkbox принятия рисков и нажмите
   **Enable Local execution**. Подтверждение сохраняется на сервере, а не в браузере.
4. Создайте новую Direct-сессию или feature. Уже привязанные сессии/features сохраняют
   свою среду; смена глобального значения не меняет место исполнения существующего
   запуска и не повышает права старого legacy-запуска.

Глобальное подтверждение распространяется на проекты, использующие Local. Можно
подтвердить доступ только для отдельного проекта. Проект не может отозвать глобальное
подтверждение: для этого нужно открыть глобальные настройки.

Checkbox «не показывать sandbox warning» из старого интерфейса, `IS_CONTAINERIZED=true`
и обычное сохранение выбора Local не заменяют подтверждение нового доступа.

## Возможности и границы

- Read/LS/Glob/Grep, Write/Edit, Mkdir/Delete, TodoWrite и shell: `/bin/sh` (имя tool
  `Bash`) на Unix, PowerShell на Windows. Это не интерактивный terminal/session manager.
- Доступны абсолютные пути и файлы вне cwd с обычными правами OS-пользователя.
  Не утверждается защита `.env`, ключей, остальных проектов, `/data` и смонтированных
  томов: всё доступное пользователю сервера потенциально доступно агенту.
- Можно устанавливать зависимости, работать с бинарными файлами, создавать каталоги
  и удалять файлы. Весь проект не копируется и не ограничивается snapshot-лимитами.
  Read/Write поддерживают base64. Поиск по умолчанию пропускает dependency/build/Git
  деревья; `includeDependencies` включает их. Явный путь и shell не ограничены этим
  фильтром поиска.
- Read выдаёт ограниченные порции с `nextOffset`/`nextLine`. Edit ограничен 2 MiB за
  вызов; для больших файлов используется shell. Это ограничения отдельных сообщений,
  а не ограничение размера проекта или бинарных зависимостей.
- Write публикует файл через temp + rename и сохраняет режим существующего файла.
  Опциональный SHA-256 помогает обнаружить устаревшее содержимое. Это не транзакция
  между процессами и не гарантия отсутствия внешних concurrent writes.
- По умолчанию Local tool timeout — 180 секунд, бюджет agent query — 15 минут;
  сохранённые серверные limits имеют приоритет. Вывод shell ограничен 12 KB.
  Прежние legacy defaults не увеличиваются автоматически. Общий верхний предел
  `toolTimeoutMs` теперь 600000; бюджет maxDuration/maxTurns продолжает действовать.
- Planning с `readOnly: true` не получает shell, Write, Edit, Mkdir или Delete.
  Text-only запросы не получают инструменты и не требуют Local-подтверждения.
- Автоматические Direct pipeline tests используют ту же привязку feature и Local
  backend, а не скрытый запуск через старый host TestRunnerService.

## Отмена, ошибки и перезапуск

На Unix обычное дерево процессов запускается отдельной process group. При отмене,
timeout и завершении shell группа останавливается; дочерние фоновые процессы этой
группы не предназначены для постоянных dev servers. Windows использует taskkill /T.
Если завершение не удалось проверить, возвращается явная ошибка cleanup, а не успех.

Local не обеспечивает изоляцию процессов: самостоятельно отделившийся через setsid
процесс, системная служба или внешняя работа могут пережить команду. Filesystem I/O
и отмена не являются транзакцией; выполненные изменения не откатываются.
После прерывания нужно проверить состояние, а не слепо повторять команду.
[Node child processes](https://nodejs.org/docs/latest-v22.x/api/child_process.html),
[Node filesystem cancellation](https://nodejs.org/docs/latest-v22.x/api/fs.html).

Привязка хранится в `{DATA_DIR}/execution-environments/bindings/`; в chat metadata
также сохраняется её описание, а Direct checkpoints содержат ID привязки. Сохраняются
тип среды, cwd/проект и legacy policy snapshot, но не API-ключи и runtime objects.
Рестарт сервера не выбирает новую среду для уже привязанной сессии/feature.

Подтверждение хранится на сервере и не сбрасывается при перезагрузке страницы.
В контейнере оно привязано к постоянному ID установки в
`{DATA_DIR}/execution-environments/container-installation.json` и OS-пользователю,
а не к временному hostname контейнера. Пересоздание контейнера с тем же томом данных,
путём DATA_DIR и пользователем сохраняет Local и Auto fallback подтверждения.
Удаление ID установки, смена пользователя или переход из контейнера на хост требуют
повторного подтверждения. Вне контейнера сохраняется привязка к identity сервера,
включая hostname. Старые подтверждения, уже потерявшие актуальность из-за смены
hostname до этого исправления, нужно подтвердить один раз заново; они не включаются
автоматически. Действующее старое подтверждение принимается на исходном сервере;
для устойчивости к следующему пересозданию контейнера его нужно обновить через UI.
После подтверждения Local-привязка может обновить identity, не меняя cwd/тип среды.
Это не возобновляет незавершённые команды автоматически. Старые legacy bindings с
другой identity не мигрируют автоматически.

**Revoke Local confirmation** блокирует последующие запросы, в том числе в уже
привязанных Local-сессиях. Текущий запрос сохраняет выданное разрешение до завершения;
для его немедленной остановки используется обычная кнопка Stop.

## Совместимость

Установки без новой явно выбранной среды остаются в прежнем Direct legacy backend.
Его серверные настройки сохранены; отдельный Direct permissions UI удалён в пользу
общей настройки и явной миграции. Права старых сессий не расширяются.

Docker, Auto и SSH уже исполняют Direct tools, см. отдельные Docker/SSH guides.
Ранее привязанные Local-запуски сохраняют Local, даже если default изменился.
Вызовы модели без tools продолжают работать независимо от этих режимов.

С этапа 5.2a явно выбранный Local и его подтверждение/привязка применяются также к
CLI/SDK chat/features; сам Local provider сохраняет свои штатные инструменты и auth.
Не настроенные установки сохраняют legacy-поведение. Remote adapters Cursor/Gemini/
OpenCode и ограничения SDK описаны в [CLI guide](execution-environments-cli.md).
Основной Git UI подключён к средам в 5.3b, ограничения описаны в [Git guide](execution-environments-git.md).
Ручные terminals и dev-server ещё используют прежние механизмы: глобальный Docker/SSH
не обещает изоляцию всего приложения.

Реальные файловые и process-tree тесты выполнены на Linux. Ветки macOS/Windows
реализованы, но на этих системах пока не проверены. Браузерный smoke использует
временный сервер/настройки и локальный mock endpoint, не настоящий модельный API.
